### 6-2. AI 배정 진행 안내에 같은 줄이 두 번, 모델 이름이 🆓로 바뀜
- 어디서: 쉬움 시나리오 6단계, 관리자가 AI 배정을 누른 뒤
- 무엇이 보였나: "1차 모델 nvidia/nemotron-3.5-super-vl🆓 성공 (7.0초)"가 두 번 나옴
- 원인: 진행 중에 그린 기록을 지우지 않고 끝난 뒤 다시 그림. 모델 이름을 마크다운으로 출력해 `:free:`가 이모지 코드로 읽힘
- 알아챈 방법: 확정 전에 진행 안내 화면을 보다가 발견(화면 `img/ai-status-duplicate-emoji.png`)
- 고침: 진행 중 기록을 지우고, 모델 이름을 코드 모양으로 출력. 화면 테스트 `tests/test_app_ui.py`가 고치기 전 코드에서 실패하는 것을 확인함. 커밋 `ffa3324`
- 고친 뒤 확인: 부록 2(중간) 11단계 AI 배정에서 기록이 한 번만, 모델 이름이 🆓 없이 나옴(화면 `img/ai-status-fixed.png`)

### 6-3. 시나리오 테스트가 너무 느림 (질의 7번)
- 어디서: 연습 시나리오 3개 자동 테스트
- 무엇이 보였나: 테스트가 5분이 넘도록 끝나지 않음
- 원인: 화면 상태를 읽을 때 DB 질의를 7번 함. 내 PC에서 DB까지 질의 1번에 0.3~0.7초
- 고침: 질의 1번으로 합침. 그 뒤 시나리오 3개 테스트가 모두 통과함(첫 커밋 `65f3691` 전에 고쳐 커밋 근거는 없음)

### 6-4. 응답 길이 한도(max_tokens)를 6000으로 너무 작게 잡아 "빈 응답"이 남
- 어디서: AI 배정용 모델 시험(어려움 시나리오 마감 뒤 상태)
- 무엇이 보였나: 여러 모델이 60~90초 뒤 "빈 응답". 클로드는 처음에 모델이 나쁜 것으로 보고 다른 모델로 바꾸려 함
- 알아챈 방법: 모델의 원래 응답을 직접 열어 봄. 작은 문제에서는 같은 모델이 정답을 냈고, 생각(reasoning)에 수천 토큰을 쓰고 있었음. 한도를 16000으로 늘리자 실패했던 `nemotron-3-ultra`(395초)와 `dots-3-note-preview`(74초)가 검사를 통과함. 1차 모델도 6707토큰을 써서 6000 한도로는 언제든 빈 응답이 날 수 있었음
- 덧붙여 확인: 생각을 끄면(reasoning enabled=false) 2~6초 만에 답하지만 규칙을 어기는 배정안을 냄
- 고침: max_tokens 16000(뒤에 24000으로 다시 늘림. 1차 모델 속도가 초당 약 180토큰이라 16000이면 약 88초에서 멈춰 120초를 다 못 쓰기 때문), 모델 순서를 1차 `nemotron-3.5-super-vl` → 2차 `dots-3-note-preview` → 3차 `gemma-4-31b-it`로 바꿈. 고친 뒤 1차 모델이 22초에 검사를 통과함. 커밋 `8ffbb55`

### 6-5. 역할 값 제약에 공고에 없는 7번째 값('관리자')을 넣음
- 어디서: `schema.sql` 의 `tf_students.main_role` 제약
- 무엇이 잘못됐나: 공고 5절은 "main_role 과 role 에 check 를 설정해 6개 역할 밖의 값을 막음"인데, 클로드가 관리자 행을 넣으려고 '관리자'를 7번째 값으로 허용함
- 알아챈 방법: 마감 날 공고 PDF를 다시 읽고 앱과 한 항목씩 비교하다 발견
- 고침: 관리자의 main_role 을 비우고(null) 6개 역할만 허용. 실제 DB에도 같은 변경을 실행하고 그 SQL을 `schema.sql` 끝에 남김. 학생에게 '관리자'를 넣으면 막히는 것을 확인. 커밋 번호는 커밋 뒤 적기
- 같이 고친 것: `requirements.txt` 가 `streamlit>=1.40` 이었는데, 앱이 쓰는 기능(컨테이너 key, 번역 막기 스크립트)은 더 새 버전이 필요해 시험한 버전 `streamlit==1.66.1` 로 고정

### 7-3. 명단 올리기가 느림
- 어디서: 부록 2(중간) 시작 전, 관리자가 `중간.csv`로 처음 상태를 만들 때
- 무엇이 보였나: 단추를 누른 뒤 화면이 5초 넘게 멈춤
- 원인: 학생을 한 명씩, 보조 역할도 하나씩 DB에 넣어 왕복이 30번 가까이 됨(내 PC에서 DB까지 왕복 한 번에 0.3~0.7초). 비밀번호 해시 16개도 차례로 만들어 약 2초 걸림
- 잰 값(어려움 명단 16명, 끝에 되돌려 실제 DB는 바꾸지 않고 잼): 고치기 전 16.4초, 17.3초 → 한 번에 넣게 고친 뒤 5.1초 → 해시를 동시에 만든 뒤 3.0초, 2.8초
- 왜 중요한가: 채점 프로그램은 화면이 바뀌기를 7초까지 기다림
- 확인: 쉬움, 중간, 어려움 명단 모두 학생, 주 역할, 보조 역할이 CSV와 똑같이 들어감
- 고침: 커밋 `b604b15`

### 7-4. 배정안 확정이 느림
- 어디서: 부록 2(중간) 11단계, 관리자가 배정안 확정을 누를 때
- 무엇이 보였나: 확정 결과가 7초 가까이 걸려서야 나옴
- 원인: 배정된 학생을 한 명씩 팀에 넣으면서, 한 명마다 빈 자리 번호를 DB에서 찾고 넣어 왕복이 학생 수의 두 배(8명이면 16번)가 됨
- 잰 값(중간 시나리오 확정 상태에서 배정된 8명을 빼고 다시 확정, 끝에 되돌려 실제 DB는 그대로): 고치기 전 6.76초 → 고친 뒤 2.10초, 2.14초
- 고침: 빈 자리 번호를 이미 읽은 상태로 계산하고 학생들을 한 번에 넣음. 지원, 투표로 팀원이 될 때도 같은 방식으로 왕복을 줄임
- 확인: 확정 뒤 규칙 위반 없음, 자리 번호 겹침 없음. 연습 시나리오 3개를 한 트랜잭션 안에서 돌리고 되돌리는 방식으로 모두 통과
