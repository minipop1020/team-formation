# 팀 프로젝트 팀 편성 웹 앱

학생들이 팀 프로젝트를 위한 팀을 스스로 편성하는 웹 앱. 지원과 팀원 투표로 팀을 만들고, 모집 마감 뒤 팀이 없는 학생은 AI가 배정안을 내며, 앱이 배정안을 규칙으로 검사한다.

## 3. 고른 해결 방법
| 기능 | 고른 해결 | 만든 방법 |
|---|---|---|
| 다른 사람의 변경 보기 | 어려운 해결 | `st.fragment(run_every=3)`로 3초마다 팀 목록과 투표 상황을 다시 그림 |
| 필수 포함 역할을 지킬 수 없는 팀 | 어려운 해결 | 지원할 때와 승인 직전에, 지원자가 들어간 뒤 남는 자리 수가 아직 채우지 못한 필수 포함 역할 수보다 적으면 막음(`tf/rules.py` 의 `join_block_reason`) |
| 같은 팀에 대기 중인 지원이 여럿 | 어려운 해결 | 팀원 모두가 찬성해 승인하려는 순간에 정원, 주 역할 중복, 필수 포함 역할 자리를 다시 검사하고, 어기면 거절 |
| 마지막 자리에 두 명이 동시에 들어감 | 어려운 해결 | `tf_members` 의 `(team_id, slot_no)` 기본 키와 `student_id` 유일성 제약(`schema.sql`). 쓰기 동작은 DB 잠금으로 한 줄로 세움 |
| AI 응답이 늦을 때 | 어려운 해결 | 모델을 부른 때부터 전체 대기 시간을 재서 120초가 되면 끊고 다음 모델로 넘어감(`tf/ai.py` 의 `call_with_deadline`) |
| 3차 모델까지 실패 | 어려운 해결 | 배정안 검사 5가지를 모두 통과하는 배정을 모든 경우를 따져 찾음(`tf/rules.py` 의 `solve`) |
| AI 대기 중 화면 | 어려운 해결 | "AI가 생각하는 중 · ○차 모델 … 의 응답을 기다리는 중 (경과 초 / 120초)"를 보여 줌 |
| DB(Supabase)가 일시정지되지 않게 | 어려운 해결 | (만든 뒤 적기) |

## 4. 쓴 모델 3개
- 1차 `nvidia/nemotron-3.5-super-vl:free`
- 2차 `dots-studio/dots-3-note-preview:free`
- 3차 `google/gemma-4-31b-it:free`

요청에는 `reasoning: {"effort": "low"}`, `max_tokens: 24000`을 준다. 이 모델들과 값으로 정한 까닭은 아래 "5. 오픈라우터 AI 모델 호출 실패 사례"와 "6. 클로드가 잘못된 추론이나 답변을 한 사례"의 1번에 있다.

## 5. 오픈라우터 AI 모델 호출 실패 사례
AI 배정에 쓸 모델을 고르려고, 앱의 AI 호출 코드(`tf/ai.py`)로 어려움 시나리오(부록 3)의 마감 뒤 상태를 무료 모델들에 보냄. 시험 스크립트의 실행 출력은 [docs/모델 시험 기록.md](docs/모델%20시험%20기록.md)에 그대로 옮겨 둠.

- 처음 정한 2차 모델 `nvidia/nemotron-3-ultra-550b-a55b:free`는 91.2초 뒤 형식이 틀린 응답, 3차 모델 `cohere/north-mini-code:free`는 86.7초 뒤 빈 응답을 냄(모델 시험 기록의 시험 1)
- 다른 후보 6개도 빈 응답 2개, HTTP 429(사용량 제한) 2개, HTTP 503 1개, 형식 오류 1개로 모두 실패함(시험 2)
- 응답 길이 한도를 늘린 뒤 `nvidia/nemotron-3.5-lightning:free`가 규칙을 어긴 배정안을 내서 앱의 배정안 검사가 걸러 냄(시험 4). 생각(reasoning)을 끈 모델 3개의 배정안도 모두 검사에서 걸러짐(시험 5)
- 이 결과로 2차, 3차 모델을 바꾸고 응답 길이 한도를 늘림(커밋 `8ffbb55`)

## 6. 클로드가 잘못된 추론이나 답변을 한 사례
1. **응답 길이 한도를 너무 작게 잡음**: 클로드가 `max_tokens`를 6000으로 정했고, 여러 모델이 60\~90초 뒤 "빈 응답"을 내자 처음에는 모델이 나쁘다고 보고 모델만 바꾸려 함. 응답 원문을 열어 보니 작은 예제에서는 같은 모델이 정답을 냈고, 답하기 전에 생각에 수천 토큰을 쓰고 있었음. 한도를 늘리자 실패했던 모델이 검사를 통과함. 1차 모델도 6707토큰을 써서 6000으로는 언제든 빈 응답이 날 수 있었음. 120초 동안 쓸 수 있는 양을 따져 24000으로 정함(근거: [docs/모델 시험 기록.md](docs/모델%20시험%20기록.md) 시험 3\~5, 커밋 `8ffbb55`)
2. **AI 배정 진행 안내에 같은 줄이 두 번, 모델 이름이 🆓로 바뀜**: 진행 중에 그린 기록을 지우지 않았고, 모델 이름을 마크다운으로 출력해 `:free:`가 이모지 코드로 읽힘. 쉬움 시나리오 6단계에서 화면을 보다 알아챔(화면 [img/ai-status-duplicate-emoji.png](img/ai-status-duplicate-emoji.png)). 커밋 `ffa3324`에서 고치고, 화면 테스트(`tests/test_app_ui.py`)가 고치기 전 코드에서 실패하는 것을 확인함. 중간 시나리오 11단계에서 고친 화면을 확인함(화면 [img/ai-status-fixed.png](img/ai-status-fixed.png))
3. **역할 값 제약에 공고에 없는 7번째 값을 넣음**: 공고 5절은 역할을 6개로 막으라고 하는데, 클로드가 관리자 행을 넣으려고 `main_role`에 '관리자'를 7번째 값으로 허용함. 마감 날 공고를 다시 읽고 앱과 한 항목씩 비교하다 알아챔. 커밋 `a2f72b6`에서 관리자의 역할을 비우고 6개만 허용하게 고침(실제 DB에 실행한 SQL은 `schema.sql` 끝에 남김)
4. **조사 오류**: 학생 화면 맨 위에 "학생로 로그인함"이 나옴. 쉬움 시나리오 화면에서 알아채고 커밋 `10239d4`에서 "학생으로 로그인함"으로 고침

## 7. 내 앱에서 발견한 문제점과 개선 필요 사항
연습용 시나리오를 직접 해 보며 찾은 것들이다. 1~4번은 발견한 뒤 고친 문제이고(고친 커밋을 함께 적음), 5번은 공고 규칙대로 동작해서 고칠 필요는 없다고 보고 그대로 둔 개선 사항이라 나눠 적었다.

1. **크롬 자동 번역이 켜진 탭에서 투표 수가 갱신되지 않음**: 부록 1(쉬움) 4단계에서 학생1이 학생7의 지원에 찬성했는데, 학생1 탭은 "찬성 1/2", 학생4 탭은 계속 "찬성 0/2"로 보임. DB에는 찬성이 저장되어 있었음. 크롬 번역이 화면 글자를 바꿔치기해 3초마다 다시 그린 숫자가 반영되지 않은 것. 로그인 화면의 "비밀번호"도 "포스틱"으로 보였음(화면 [img/vote-student4-tab-stale.png](img/vote-student4-tab-stale.png), [img/vote-student1-tab.png](img/vote-student1-tab.png), [img/translate-login-label.png](img/translate-login-label.png), [img/translate-team-view.png](img/translate-team-view.png)). 커밋 `10239d4`에서 페이지를 번역하지 않게 표시함
2. **명단 올리기가 느림**: 부록 2(중간) 시작 전 명단을 올리니 화면이 5초 넘게 멈춤. 학생과 보조 역할을 한 명씩 DB에 넣어 왕복이 30번 가까이 됐음. 16명 명단 기준 16.4초 → 2.8초로 줄임(커밋 `b604b15`). 채점 프로그램은 화면이 바뀌기를 7초까지 기다리므로 그대로 두면 채점이 멈출 수 있었음
3. **배정안 확정이 느림**: 부록 2(중간) 11단계에서 확정이 7초 가까이 걸림. 학생마다 빈 자리 번호를 DB에서 찾고 넣었기 때문. 6.76초 → 2.1초로 줄임(커밋 `9154c71`)
4. **결과 안내가 예전 결과를 계속 보여 줌**: 부록 3(어려움) 8단계에서 학생6 화면 맨 위는 "대기: 팀2 팀원 2명의 투표를 기다림"인데 팀2 카드는 "찬성 2/3"으로 보임. 학생7은 팀1 팀원이 된 뒤에도 맨 위 안내가 "대기"로 남음(화면 [img/hard-step8-stale-result.png](img/hard-step8-stale-result.png), [img/hard-step3-stale-after-approved.png](img/hard-step3-stale-after-approved.png)). 결과 안내는 단추를 누른 때의 결과로 두고, 그 아래에 "그 뒤 바뀐 상태"와 "나의 지원 내역" 표를 더함(커밋 `ca52338`)
5. **고치지 않은 개선 사항: 지원 단추가 회색인 이유가 안 보임**: 부록 2(중간) 8단계에서 학생12가 팀4에 지원한 뒤 모든 팀의 지원 단추가 회색이 됨. 공고 2.8절대로 결과를 기다리는 지원이 있으면 지원 단추를 비활성화한 것이라 규칙상 고칠 필요는 없음. 다만 화면에 이유가 나오지 않아 처음에는 고장인 줄 알았음. 회색 단추 옆에 이유(결과를 기다리는 지원이 있음, 이미 팀이 있음, 모집 마감)를 보여 주면 더 알기 쉬움

## 시험한 방법
- 연습용 시나리오 3개를 브라우저 탭을 학생마다 열어 직접 처음부터 끝까지 해 봄. 셋 다 결과 안내가 기대 결과와 같았고, 확정한 팀이 모두 규칙을 지킴
- 자동 테스트: 규칙(`tests/test_rules.py`), AI 실패 처리(`tests/test_ai.py`), 화면(`tests/test_app_ui.py`), 연습용 시나리오(`tests/test_scenarios.py`), 무작위 시험(`tests/test_rules_random.py`, `tests/test_random_scenarios.py`)

## 실행 방법(내 PC)
1. `pip install -r requirements.txt`
2. `.env.example`을 참고해 `.env`에 `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD`를 넣음(깃허브에는 올리지 않음)
3. Supabase에 `schema.sql`을 실행
4. `streamlit run streamlit_app.py`
